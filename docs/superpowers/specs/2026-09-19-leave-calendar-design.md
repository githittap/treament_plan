# 연차 전용 캘린더 설계서

> 작성일: 2026-09-19
> 상태: A안 승인 후 구현 전 설계
> 대상: `treament_plan/hr.html`의 기존 `연차현황` 탭

## 1. 목표

기존 상단 `연차현황` 탭의 사용자 표시 라벨을 `연차캘린더`로 바꾸고, 승인된 연차만 보여 주는 전용 화면으로 확장한다. 내부 식별자 `key: 'leavestatus'`는 유지한다. 한 화면 안에서 `달력 보기`와 `목록 보기`를 전환할 수 있게 하며, 달력에서는 같은 날짜의 승인 연차를 신청 시각 순서로 표시한다. 목록 보기에서는 기존 연차현황 표의 확인 목적을 유지한다.

이번 설계의 범위는 화면·조회·표시 규칙과 테스트 설계다. 구현은 이 설계서에 대한 최종 확인 뒤에 별도로 진행한다.

## 2. 현재 구조와 변경 경계

현재 `hr.html`에는 다음 구조가 있다.

- `TABS`에 `key: 'leavestatus'`, `label: '연차현황'` 탭이 있고 네 역할(`staff`, `manager`, `chief`, `owner`)에 노출된다. 구현 시 `key`는 유지하고 사용자 표시 라벨만 `연차캘린더`로 바꾼다.
- 라우터는 `TAB === 'leavestatus'`일 때 `renderLeaveStatus(m)`을 호출한다.
- `renderLeaveStatus()`는 `leave_requests`에서 선택 월과 겹치는 행을 조회하고, 현재는 상태 제한 없이 기존 표에 이름·종류·기간·일수·상태·사유를 출력한다.
- `leave_requests`에는 `id`, `user_id`, `type`, `date_from`, `date_to`, `days`, `status`, `owner_at`, `created_at`이 이미 있다.
- 기존 근무표는 이미 `status = '승인'` 조건과 `date_from <= 범위 종료`, `date_to >= 범위 시작` 방식으로 승인 연차를 조회한다.

구현 시 제품 코드 변경 파일은 `treament_plan/hr.html` 하나로 제한한다. 자동테스트는 기존 테스트 파일을 수정하거나 `tests/leave-calendar.test.js`를 새로 추가하는 것을 허용한다. DB 스키마·SQL, RLS 정책, Edge Function, 다른 제품 코드 파일은 변경하지 않는다. 이 설계 단계에서는 이 설계서만 생성·수정한다.

## 3. 승인된 A안의 확정 규칙

### 3.1 공개 범위와 상태 필터

- 모든 역할(`staff`, `manager`, `chief`, `owner`)은 전 직원의 `status = '승인'` 연차만 본다.
- `대기`, `1차승인`, `반려`, `취소`는 연차 전용 달력과 목록에 표시하지 않는다.
- 기존 `연차` 신청 화면, 승인 대기 화면, 개인 신청 내역의 동작은 이 설계의 대상이 아니다.
- 조회 결과가 0건인 것과 조회가 실패한 것은 구분한다. 실패를 빈 달력 또는 “내역 없음”으로 처리하지 않는다.

### 3.2 역할별 표시

| 필드 | 직원(staff) | 매니저(manager) | 실장(chief) | 원장(owner) |
|---|---:|---:|---:|---:|
| 직원 이름 | 표시 | 표시 | 표시 | 표시 |
| 승인 연차의 날짜 | 표시 | 표시 | 표시 | 표시 |
| 다일 연차의 날짜별 순번 | 표시 | 표시 | 표시 | 표시 |
| 신청 시각 `created_at` | 숨김 | 숨김 | 숨김 | 표시 |
| 승인 시각 `owner_at` | 숨김 | 숨김 | 숨김 | 표시 |
| 연차 종류 `type` 및 `type_note` | 숨김 | 숨김 | 숨김 | 표시 |
| 기존 목록의 기간·일수 | 표시 | 표시 | 표시 | 표시 |

달력에서는 일반 역할에 정확한 시각을 노출하지 않고 순번만 노출한다. 원장에게는 동일한 항목의 상세 정보에 `created_at`, `owner_at`, `type`을 함께 보여 준다. 시각 표시는 기존 `Asia/Seoul` 기준 날짜·시간 포맷을 따른다.

### 3.3 날짜별 정렬과 순번

한 승인 행이 `date_from`부터 `date_to`까지 포함하면 포함된 모든 날짜에 같은 신청을 확장한다. 날짜별로 다음 키를 오름차순 정렬한다.

1. `created_at` 오름차순
2. `created_at`이 같은 경우 `id` 오름차순

정렬된 결과의 1-based 위치를 그 날짜의 순번으로 사용한다. 예를 들어 같은 날짜에 두 건이면 `① 이름`, `② 이름`으로 표시한다. 순번은 신청 행 전체의 순번이 아니라 각 날짜에 확장된 결과 집합에서 다시 계산한다.

`created_at`이 null인 기존 데이터가 발견되면 임의의 현재 시각을 만들지 않는다. 조회 결과의 정렬 안정성을 위해 null을 마지막으로 두고 `id` 오름차순을 적용한다. 정상 스키마의 기본값은 `now()`이므로 이 분기는 호환성 보호용이다.

### 3.4 월 경계와 다일 연차

- 선택 월의 시작일을 `monthFrom`, 종료일을 `monthTo`로 계산한다.
- 서버 조회 조건은 `status = '승인'`, `date_from <= monthTo`, `date_to >= monthFrom`이다.
- 화면에 확장할 때 각 행의 시작일을 `max(date_from, monthFrom)`, 종료일을 `min(date_to, monthTo)`로 잘라 선택 월 안의 날짜만 만든다.
- 월말에서 다음 달로 이어지는 연차는 선택 월의 마지막 날까지 표시한다.
- 다음 달에서 시작해 선택 월에 걸치는 연차도 선택 월의 첫날부터 표시한다.
- 단일 날짜 연차는 해당 날짜 한 칸에만 표시한다.

## 4. 화면 설계

### 4.1 탭과 상태

기존 탭 키 `leavestatus`와 권한 노출은 유지한다. 탭 내부 상태는 다음 세 가지다.

- `LVSTATUS_MONTH`: 선택 월. 초기값은 오늘이 포함된 `YYYY-MM`.
- `LVSTATUS_VIEW`: `calendar` 또는 `list`. 초기값은 `calendar`.
- 조회 결과 및 오류 상태: 현재 월을 다시 렌더링할 때마다 새로 계산한다.

월 선택기와 보기 전환 버튼은 같은 카드 상단에 둔다. 보기 전환은 로컬 화면 상태만 바꾸며 DB에 저장하지 않는다.

### 4.2 달력 보기

달력은 기존 `renderCalendar()`의 월 그리드 스타일을 재사용하되, 연차 전용 데이터만 사용한다.

- 제목은 `🏖 연차 캘린더`로 표시한다.
- 일요일부터 토요일까지 7열 월 그리드를 사용한다.
- 선택 월에 포함되는 날짜 칸을 생성한다.
- 각 날짜 칸에는 승인 연차만 `① 이름`, `② 이름` 형식으로 표시한다.
- 같은 이름이 같은 날짜에 여러 신청으로 중복되면 신청 행 기준으로 표시한다. 숨은 중복 제거를 하지 않는다.
- 일반 역할은 이름과 순번만 본다.
- 원장은 이름·순번과 함께 신청 시각, 승인 시각, 연차 종류를 상세 항목으로 본다. 긴 정보는 날짜 칸을 깨뜨리지 않도록 항목 내부 줄바꿈을 허용한다.
- 날짜 칸을 펼치거나 상세 영역을 여는 기존 캘린더 상호작용이 있다면 그 패턴을 따르되, 새 기능을 위해 전역 동작을 바꾸지 않는다.

달력에 승인 연차가 없을 때는 오류가 아닌 빈 상태로 `선택한 달의 승인 연차가 없습니다.`를 표시한다.

### 4.3 목록 보기

목록 보기는 기존 연차현황 표를 보존한다. 다만 전 직원에게 승인 연차만 공개한다.

- 일반 역할의 열: 이름, 기간, 일수.
- 원장의 열: 이름, 연차 종류, 기간, 일수, 신청 시각, 승인 시각.
- 상태·사유·특별사정·대기/반려/취소 행은 목록에서 제거한다. 화면 제목과 안내 문구도 “승인된 연차” 기준으로 맞춘다.
- 목록의 기본 정렬은 `date_from` 오름차순, 같은 시작일은 `created_at` 오름차순, 동률은 `id` 오름차순이다.
- 원장에게만 정확한 시각을 노출한다. `manager`·`chief`를 포함한 비원장 역할에는 시각 열 자체를 렌더링하지 않는다.

목록 보기의 목적은 날짜별 순번 확인이 아니라 기존 표 방식으로 기간·일수를 확인하는 것이다. 날짜별 순번은 달력 보기에서만 표시한다.

## 5. 데이터 조회와 변환 설계

### 5.1 조회 필드

`leave_requests`에서 다음 필드만 조회한다.

```text
id, user_id, type, type_note, date_from, date_to, days,
status, owner_at, created_at
```

조회는 다음 조건을 모두 사용한다.

```text
status = '승인'
date_from <= monthTo
date_to >= monthFrom
```

조회 단계에서 `.order()`를 사용하더라도 날짜별 순번의 최종 기준은 클라이언트 변환 단계에서 `created_at`, `id`로 다시 명시적으로 정렬한다. 서버 정렬 순서에 순번 의미를 의존하지 않는다.

### 5.2 이름 결합

기존 `nameOf(user_id)` 또는 현재 직원 프로필 캐시를 사용한다. 새 직원 조회 테이블·DB 컬럼·RLS 정책은 만들지 않는다. 이름을 찾지 못한 경우 사용자 ID 전체를 무분별하게 노출하지 않고, 기존 화면의 이름 표시 규칙에 맞는 안전한 대체 텍스트를 사용한다.

### 5.3 날짜 확장 의사코드

구현 시 함수 경계를 다음처럼 유지한다. 실제 함수명은 기존 전역 함수와 충돌하지 않도록 구현 전에 확인한다.

```js
function buildLeaveCalendarIndex(rows, monthFrom, monthTo) {
  const byDate = {};
  for (const row of rows) {
    const start = maxDate(row.date_from, monthFrom);
    const end = minDate(row.date_to, monthTo);
    for (let date = start; date <= end; date = addDays(date, 1)) {
      (byDate[date] ||= []).push(row);
    }
  }
  for (const date of Object.keys(byDate)) {
    byDate[date].sort(compareLeaveRowsByCreatedAtThenId);
    byDate[date] = byDate[date].map((row, index) => ({
      row,
      rank: index + 1,
      date
    }));
  }
  return byDate;
}
```

위 의사코드는 설계상의 동작을 고정하기 위한 것이며 현재 파일에 추가할 구현 코드가 아니다. 날짜 문자열은 기존 프로젝트의 `addDays`·`YYYY-MM-DD` 처리 규칙을 따르고, 브라우저의 UTC 변환으로 날짜가 밀리지 않게 한다.

### 5.4 오류 처리

조회 결과에 `error`가 있으면 달력과 목록을 모두 그리지 않고 카드 안에 다음 정보를 표시한다.

- `연차 정보를 불러오지 못했습니다.`라는 명확한 제목
- Supabase가 반환한 오류 메시지의 안전한 이스케이프 출력
- 재시도 방법으로 새로고침 안내

오류 상태에서 `rows = []`로 대체하거나 `이번 달 내역 없음`을 표시하지 않는다. 이름 결합 실패와 연차 조회 실패도 혼동하지 않는다. 연차 조회가 성공하고 결과가 0건인 경우만 정상 빈 상태로 처리한다.

## 6. 권한·보안 경계

- 이 기능은 기존 `leave_requests`의 읽기 정책을 사용한다.
- 새 DB 컬럼, 뷰, 함수, RLS 정책, 권한 확대를 추가하지 않는다.
- 화면에서 숨기는 것만으로 DB 보안이 강화된다고 주장하지 않는다. 기존 RLS가 반환하는 행 범위 안에서 `status = '승인'` 필터와 역할별 렌더링을 적용한다.
- 비원장 화면으로 전송할 필요가 없는 owner 전용 필드는 구현 시 역할에 따라 선택 필드를 분리할 수 있으나, 기존 RLS·조회 계약을 깨지 않는 최소 변경으로 한다.
- 신청 시각과 승인 시각은 비원장에게 표시하지 않으며, 순번은 시각 자체가 아니라 날짜별 상대 순서만 의미한다.

## 7. 테스트 설계

구현 단계에서 기존 프로젝트의 테스트 방식과 `hr.html` 내 테스트 훅을 먼저 확인한 뒤 다음 시나리오를 모두 검증한다. 자동테스트는 기존 테스트 파일을 수정하거나 `tests/leave-calendar.test.js`를 추가할 수 있으며, 이 설계 단계에서는 테스트 파일이나 제품 코드에 손대지 않는다.

### 7.1 역할별 노출

동일한 승인 연차 데이터에 대해 네 역할로 렌더링한다.

- `staff`, `manager`, `chief`: 이름·날짜·순번·목록의 기간·일수만 표시한다.
- 세 역할 모두 `created_at`, `owner_at`, `type`, `type_note`의 값과 열이 보이지 않는다.
- `owner`: 신청 시각·승인 시각·연차 종류가 보인다.
- 모든 역할은 같은 승인 연차 행 집합을 본다.

### 7.2 승인만 필터

`대기`, `1차승인`, `반려`, `취소`, `승인`을 각각 포함한 fixture를 사용한다. 달력과 목록에는 `승인` 행만 남아야 한다. 승인 행이 0건이면 정상 빈 상태가 나오고, 다른 상태 행이 대신 보이면 실패다.

### 7.3 날짜별 정렬과 동률

같은 날짜에 다음 세 행을 둔다.

- `created_at`이 이른 id 20
- `created_at`이 늦은 id 10
- `created_at`이 앞의 행과 같은 id 5

기대 순서는 시간 오름차순 후 id 오름차순이며, 표시 순번은 `①`, `②`, `③`이다. 서로 다른 날짜에 걸친 동일 행은 각 날짜에서 다시 `①`부터 계산한다.

### 7.4 다일 연차

`date_from = 2026-09-10`, `date_to = 2026-09-12`인 한 행이 9월 10·11·12일에 모두 표시되는지 확인한다. 9월 11일에 다른 신청을 추가하면 그 날짜에서만 순번이 재계산되어 두 항목이 각각 `①`, `②`가 되어야 한다.

### 7.5 월 경계

- 8월 30일~9월 2일 행을 9월 선택 화면에서 9월 1·2일에 표시한다.
- 9월 29일~10월 2일 행을 9월 선택 화면에서 9월 29·30일에 표시한다.
- 8월 전용 행과 10월 전용 행은 9월 화면에 표시하지 않는다.
- 조회 조건이 선택 월과 겹치는 행을 빠뜨리지 않는지 확인한다.

### 7.6 목록 보기 보존

보기 전환으로 목록을 선택하면 승인 행의 기존 기간·일수 확인이 가능해야 한다. 달력으로 돌아갔을 때 같은 월과 같은 승인 데이터가 유지되어야 한다. 목록에서 순번을 일반 표 순번으로 잘못 표시하지 않는다.

### 7.7 조회 실패

`leave_requests` 조회가 오류를 반환하도록 모킹한다. 달력과 목록 어느 쪽에서도 빈 상태 문구가 나오지 않고, “연차 정보를 불러오지 못했습니다” 오류가 표시되어야 한다. 오류 메시지는 HTML로 해석되지 않도록 이스케이프한다.

### 7.8 정적 검증

구현 후 최소한 다음을 확인한다.

- 허용된 변경 범위가 제품 코드 `hr.html`과 연차캘린더 자동테스트 파일뿐인지 `git status --short`로 확인한다.
- `status = '승인'` 필터가 연차 전용 조회에 존재하는지 확인한다.
- 비원장 렌더링 경로에 `created_at`, `owner_at`, `type`이 출력되지 않는지 확인한다.
- 조회 오류 분기가 빈 배열로 폴백하지 않는지 확인한다.
- 월 경계에서 `date_from`과 `date_to` 양쪽 비교가 모두 존재하는지 확인한다.

## 8. 구현 순서와 완료 기준

1. `hr.html`의 기존 `renderLeaveStatus()`와 전역 상태 충돌 여부를 확인한다.
2. 승인 연차 조회와 월 범위 변환을 최소 함수로 구현한다.
3. 달력 보기와 목록 보기의 역할별 필드 렌더링을 구현한다.
4. 조회 오류·빈 상태·월 전환·보기 전환을 검증한다.
5. 위 테스트 설계의 모든 시나리오를 실행하고 결과를 기록한다.

완료로 인정하는 기준은 다음과 같다.

- 전 역할에서 승인 건만 보인다.
- 달력의 모든 포함 날짜에 다일 연차가 표시된다.
- 날짜별 정렬이 `created_at` 후 `id` 기준으로 재현된다.
- 비원장에게 정확한 신청·승인 시각과 연차 종류가 노출되지 않는다.
- 원장에게만 세 owner 전용 필드가 보인다.
- 목록 보기가 기존 기간·일수 확인 기능을 보존한다.
- 조회 실패가 오류로 표시되고 빈 달력으로 위장되지 않는다.
- 구현 단계에서 DB·SQL·RLS·배포 변경이 없고, 제품 코드 변경은 `hr.html`, 자동테스트 변경은 기존 테스트 파일 또는 `tests/leave-calendar.test.js`로 제한된다.

## 9. 범위 밖

다음 항목은 이번 A안과 이 설계서의 범위에 포함하지 않는다.

- 새 캘린더 전용 DB 테이블·뷰·컬럼·인덱스·RLS 추가
- 연차 승인 절차나 상태명 변경
- 연차 신청·취소·승인 화면의 업무 흐름 변경
- 직원별 공개 범위 설정 기능
- 공휴일·근무표·캘린더 이벤트와의 통합 표시
- 알림, 구독, 이메일·문자 전송
- 과거 데이터의 `created_at`·`owner_at` 보정
- 연차 종류의 신규 분류나 계산 방식 변경

## 10. 자체검토 결과

- 승인된 요구사항을 공개 범위, 상태 필터, 정렬 동률, 역할별 필드, 다일 연차, 기존 목록 보존, 오류 처리, 테스트 설계로 각각 연결했다.
- `leave_requests.created_at`과 `owner_at`만 사용하도록 명시했고 새 DB 컬럼·RLS 변경을 제외했다.
- 월 경계의 양방향 겹침 조건과 날짜별 순번 재계산을 명시했다.
- 조회 실패와 정상 0건을 구분했다.
- 구현 대상 파일은 `hr.html`로 한정했고, 현재 작성 단계에서 수정한 파일은 이 설계서 하나다.
- 미완성 표시와 빈 항목, 승인안과 충돌하는 상태 표시 요구는 남기지 않았다.
