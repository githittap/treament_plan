# 직원허브 직무 분류 통합 설계 — 네 묶음 한눈보기

## 목적과 범위

직원별 직무를 네 가지 고정 분류로 한곳에서 관리하고, 근무표·캘린더·근로계약·관리 화면이 같은 분류를 사용하게 한다. 관리자는 네 그룹의 현재 배치를 한 화면에서 확인하고, 직원을 선택해 분류를 바꾸며, 저장 전에 변경 인원과 결과를 미리 본다. 분류 누락은 경고하고 퇴사자는 현재 배치에서 제외한다.

이 문서는 A4+A5 승인안의 설계만 확정한다. 구현 코드, 운영 데이터 변경, 운영 DB 적용, `main` 반영과 push는 포함하지 않는다. 직무 분류는 계정 권한(`staff`, `manager`, `chief`, `owner`, `deputy`)과 다른 정보이며 권한이나 화면 접근을 바꾸지 않는다.

## 확정 분류와 의미

| 저장 코드 | 화면 이름 | 포함 업무 예시 |
|---|---|---|
| `clinical_consult` | 진료·상담 | 진료실, 상담실, 통역 등 진료 또는 환자 상담 지원 |
| `sterilization_admin` | 소독·행정 | 기구 소독·멸균 및 일반 행정 지원 |
| `lab` | 기공 | 기공 작업 및 기공실 업무 |
| `desk` | 데스크 | 접수, 수납, 리셉션 업무 |

저장 코드 집합은 위 네 값으로 제한한다. 빈 값은 미지정이며, 다른 자유 입력 분류는 허용하지 않는다. 사람은 한 시점에 한 분류만 가진다. 실제 담당 업무가 여러 그룹에 걸쳐도 기본 분류 하나를 정하고, 근무표의 기존 날짜별 배치·야간 근무 등은 별도 일정 데이터로 유지한다.

## UI 구조와 동작

관리 화면의 기존 직원 권한 관리 안에 「직무 분류」 하위 영역을 둔다. 새 상단 탭을 만들지 않는다. 상단에는 재직자 전체 수, 네 그룹별 인원 수, 미지정 수를 표시한다. 본문은 네 그룹을 고정 순서(진료·상담 → 소독·행정 → 기공 → 데스크)로 나란히 보여 주고 각 그룹 안에는 이름과 현재 분류를 표시한다. 미지정자는 별도의 경고 목록에 이름을 표시한다. 계정 권한은 이 화면의 분류 표시에 섞지 않는다.

분류를 바꿀 대상자를 체크하고 하나의 새 분류를 고른 뒤 「미리보기」를 누른다. 미리보기는 현재 그룹별 인원과 변경 후 그룹별 인원, 이동 대상 이름·이전 분류·새 분류, 이동 인원 수, 저장 후 남을 미지정 인원을 보여 준다. 선택 대상 수와 실제 변경 건수가 다르면 저장할 수 없다. 사용자가 미리보기에서 「저장」을 눌렀을 때만 변경을 요청한다. 저장 중에는 중복 입력을 막고, 성공한 경우 서버 값을 다시 읽어 화면을 갱신한다.

PC에서는 네 그룹 카드를 한 줄 또는 두 줄 그리드로 배치하고, 미지정 경고 및 변경 미리보기를 그 아래에 둔다. 좁은 화면에서는 그룹 카드를 한 열로 쌓고, 대상 선택과 분류 선택을 세로로 배치한다. 표나 카드 안의 이름·상태·버튼은 가로 스크롤 없이 읽히게 한다. 미리보기는 작은 화면에서 전체 폭으로 펼치며 저장·취소 버튼을 하단에 계속 보이게 한다.

근무표와 캘린더는 공통 코드로 그룹 이름·색상·정렬 순서를 가져온다. 기존 날짜별 일정과 개인별 배치 선택은 보존하고, 행·필터·요약의 직무 표지만 공통 분류로 표시한다. 근로계약서 작성 화면은 직원 선택 시 현재 공통 분류를 표시하고, 기존 계약 역할 문구·수행업무 입력값을 자동 치환하지 않는다. 분류를 계약서에 문구로 반영하는 후속 변경은 계약 템플릿 영향 검토와 별도 승인 뒤 진행한다. 관리 화면은 같은 분류값을 편집·요약하는 유일한 UI가 된다.

## 데이터 모델과 기준값

인증 계정이 있는 직원의 정본은 `profiles.job_group`이다. `job_group`은 `clinical_consult`, `sterilization_admin`, `lab`, `desk` 중 하나 또는 `NULL`이다. `profiles.role`은 계정 권한으로 그대로 둔다. `profiles.dept`는 과거 값과 기존 호출부 호환을 위해 이 작업에서는 수정하지 않는다.

`schedule_people` 중 `profile_user_id`가 있는 행은 연결된 `profiles.job_group`를 기준값으로 사용한다. 해당 행의 기존 `department`는 일정 레코드 호환을 위해 유지하되, 새 화면에서는 분류 정본처럼 읽거나 수정하지 않는다. `profile_user_id IS NULL`인 비로그인 근무자는 그 명부 행의 `job_group`를 정본으로 쓴다. 비로그인 근무자도 같은 네 코드와 미지정 `NULL`을 사용한다. 이 구분으로 연결된 계정과 비로그인 명부 사이에 이중 편집 가능한 정본이 생기지 않는다.

근무표·캘린더·계약·관리 화면의 읽기 경로는 위 기준값을 공통 변환 함수 하나로 화면 모델에 공급한다. 분류 이름, 표시 색, 정렬은 해당 함수의 상수표에서만 정의한다. 한 화면에서 예전 `dept` 또는 `department`를 직접 분류로 표시하지 않는다. 계약 기능은 분류를 직원 선택 정보로 읽되, 계약 문구 및 과거 계약 스냅샷은 수정하지 않는다.

## 기존 값 변환

새 컬럼을 추가하는 확장형 migration에서만 변환한다. 기존 컬럼 값은 변경하지 않으며, 변환 결과가 불명확하거나 누락된 경우 자동으로 추정하지 않고 `NULL`로 남겨 미지정 경고에서 검토한다.

| 원본 위치 | 기존 값 | 새 분류 |
|---|---|---|
| `profiles.dept` | `진료실` | `clinical_consult` |
| `profiles.dept` | `데스크` | `desk` |
| `profiles.dept` | `기공팀` | `lab` |
| `profiles.dept` | `기타`, 빈 값, 기타 미등록 값 | `NULL` |
| `schedule_people.department` (비로그인 명부) | `Dr.`, `진료실`, `상담` | `clinical_consult` |
| `schedule_people.department` (비로그인 명부) | `행정` | `sterilization_admin` |
| `schedule_people.department` (비로그인 명부) | `기공실` | `lab` |
| `schedule_people.department` (비로그인 명부) | `데스크` | `desk` |
| `schedule_people.department` (비로그인 명부) | `미지정`, 빈 값, 기타 미등록 값 | `NULL` |

연결된 `schedule_people` 행의 새 `job_group`는 같은 직원의 `profiles.job_group`를 참조해 조회하며, 값 복제·역동기화하지 않는다. 기존 `schedule_people.department='미지정'`이더라도 프로필에 변환 가능한 부서가 있으면 프로필 분류를 사용한다. 같은 직원이 승인된 프로필 없이 명부에만 존재하는 경우 명부 변환 규칙을 적용한다.

## 신규 직원과 퇴사자

가입 승인으로 만들어지는 프로필과 근무명부 행은 기존 권한·승인 절차를 유지한다. 신규 프로필의 `job_group`는 `NULL`로 시작한다. 관리자는 미지정 경고에서 분류를 지정해야 하며, 분류가 미정이어도 기존 가입 승인을 자동 거부하거나 권한을 바꾸지 않는다. 비로그인 명부 신규 행도 같은 방식으로 `job_group=NULL`에서 시작하고, 명부 추가 절차는 유지한다.

재직 여부의 기준은 프로필의 `employment_status`와 `employment_effective_date`다. 기준 날짜가 유효일 이후이고 상태가 `재직`이 아니면 퇴사자로 보아 현재 배치의 네 그룹과 미지정 경고에서 제외한다. 유효일 이전 날짜를 조회하는 과거 일정은 당시 일정 스냅샷과 기존 과거 표시 동작을 사용한다. 비로그인 명부 인원은 기존 `active` 값을 재직 여부 기준으로 삼는다. 비활성 명부 인원은 현재 배치에서 제외한다. 제외는 표시 규칙일 뿐 프로필, 명부, 근무·계약·급여 이력을 삭제하거나 바꾸지 않는다.

## 저장 전 미리보기와 동시 변경

미리보기는 최신 서버 자료를 기준으로 생성한다. 다음 조건을 전부 만족해야 저장 버튼이 켜진다.

1. 선택된 대상이 한 명 이상이고 모두 현재 재직 중이다.
2. 새 분류가 네 코드 중 하나다.
3. 각 대상의 저장 전 분류가 화면에서 미리 본 값과 일치한다.
4. 변경 건수가 1 이상이며, 네 그룹별 변경 후 인원 합계가 대상 총수와 일치한다.
5. 연결된 프로필 직원은 `profiles.job_group`, 비로그인 명부 직원은 `schedule_people.job_group`에만 쓰기 대상으로 포함된다.

미리보기 생성 후 원본이 바뀌었으면 저장을 거부하고 최신 자료를 다시 불러와 새 미리보기를 요구한다. 부분 저장이 발생하면 성공·실패 대상을 각각 표시하고, 성공 여부가 불확실한 건은 다시 읽어 확정하기 전까지 성공으로 보고하지 않는다. 저장 실패 시 화면에 현재 자료를 다시 읽도록 안내하며 로컬 낙관 갱신으로 저장 성공처럼 표시하지 않는다.

## 오류와 미지정 처리

- 그룹 요약을 불러오지 못하면 빈 명단으로 오인시키지 않고 오류 문구와 재시도 버튼을 표시한다.
- 알려지지 않은 저장 코드, 기존 값 변환 실패, 미연결 프로필, 중복 연결은 미지정 경고로 모으고 자동 분류하지 않는다.
- 권한 거부 응답은 권한 부족으로 표시하고 편집 UI를 잠근다. 직무 그룹 변경은 기존 프로필·명부 변경 권한을 재사용하며 새 권한 역할을 만들지 않는다.
- 네트워크 오류·세션 만료·검증 오류·동시 변경을 구분해 표시한다. 원문 데이터나 개인정보를 오류 로그에 복제하지 않는다.
- 미지정 인원은 근무표의 기존 미지정 표시를 유지한다. 계약 미리보기는 분류가 비어 있다는 안내를 표시하되 임의로 계약 직무 문구를 생성하지 않는다.

## 로컬 migration과 rollback 설계

Migration은 로컬 브랜치에서만 작성·검증한다. `profiles.job_group`와 `schedule_people.job_group`를 nullable로 추가하고 허용값 제약을 네 코드로 제한한다. 기존 `dept`·`department` 및 일정 이력은 건드리지 않는다. 이행 SQL은 한 트랜잭션에서 컬럼 추가, 확정된 매핑의 backfill, FK 연결 무결성 및 변환 전후 행 수 점검을 수행한다. 운영 DB 연결을 사용하지 않는다.

로컬 rollback은 두 수준으로 둔다. 첫 단계는 앱 변경만 되돌리고 두 신규 nullable 컬럼은 남겨 새 값·기존값을 보존하는 호환 rollback이다. 컬럼 제거가 필요한 경우에는 신규 컬럼에 분류값이 한 건도 없고, 연결·미연결 행 수 및 기존 원본 값 점검이 migration 전 스냅샷과 일치할 때만 down migration을 실행한다. 신규 분류값이 이미 저장된 뒤에는 컬럼을 제거하지 않는다. 이 경우 로컬 자료를 별도 보존하고 호환 rollback 상태로 멈춘다. 롤백 SQL도 로컬 테스트 DB에서만 실행한다.

## 테스트 계획

구현 시 다음을 로컬 단위·통합 시험으로 확인한다.

- 네 코드만 허용되고 `NULL`은 미지정이며 알 수 없는 값이 오류 경고로 분류됨.
- 표의 모든 기존 값 매핑, 미등록 값, 빈 값, 연결 프로필 우선 규칙이 기대한 결과를 냄.
- 연결 직원은 프로필 분류를 한 번만 저장하며 비로그인 명부 직원은 명부 분류를 저장함.
- 신규 가입·신규 명부 인원은 미지정으로 시작하고 기존 승인·권한 동작이 유지됨.
- 퇴사 유효일 경계 전후와 비활성 명부 인원의 현재 배치 제외, 과거 일정 보존을 확인함.
- 미리보기 집계·이전/새 분류·변경 건수 및 저장 버튼 조건을 검증함.
- 저장 전 동시 변경, 부분 실패, 재조회 실패, 세션 만료, 권한 거부가 성공으로 오인되지 않음.
- PC 폭과 640px 이하 화면에서 네 그룹, 미지정 경고, 긴 이름, 미리보기와 버튼이 읽히고 조작 가능함.
- 근무표·캘린더·계약·관리 화면이 같은 기준값과 이름·색·정렬을 쓰고 기존 일정·과거 계약 스냅샷이 바뀌지 않음.
- migration backfill 및 무변경 down rollback을 로컬 DB에서 확인하고, 신규 분류값이 존재할 때 down migration이 중단되는지 검증함.

## 비범위와 승인 게이트

- 직무 분류 변경으로 계정 권한, 탭 접근, RLS 정책을 바꾸지 않는다.
- 신규 상단 탭, 다중 직무 선택, 직무별 급여·수당 계산, 자동 직무 추정은 추가하지 않는다.
- 과거 일정·계약·급여 행의 재분류나 삭제를 하지 않는다.
- 계약 문구·업무 설명 템플릿은 수정하지 않는다.
- 운영 DB migration, 운영 직원 자료 수정, 공개 배포, `main` push는 이 승인에 포함되지 않는다.

다음 단계는 이 설계의 사용자가 최종 확인한 뒤 로컬 구현 범위와 시험 증거를 별도로 확정하는 것이다. 운영 적용·배포·공개 또는 이 설계에서 벗어나는 데이터 변환은 각각 별도 승인을 받아야 한다.
