## 기타 지적
- 1단계의 '현재 SQL 실패 확인' 실행과 3단계 실행을 합치면 PGlite 시험이 두 번 돈다. 요구사항의 '한 번 실행'과 어긋나 보일 수 있으므로, 재현 실패 확인은 사전 확인이고 3단계가 공식 1회 실행이라고 결과에 구분해 적는 편이 좋다.
- '다른 수기 분류'의 범위를 명시해야 한다. 계획은 NULL·공백(btrim 후 빈 문자열)·'미지정'이 아닌 모든 department를 보존 대상으로 본다. 이때 확정 그룹과 뜻이 같은 값(예: 확정 clinical_consult 인물의 roster가 '진료실')과 '기타'·'Dr.'도 보존된다. 원장 문구와 맞는 보수적 해석이지만 구현결과에 이 해석을 한 줄 남기는 것이 좋다.
- profile_count=1 분기에서는 profiles.job_group 갱신이 roster 연결 판단보다 먼저 일어난다. 수기 분류 roster를 연결하지 않기로 해도 profile은 확정 그룹을 받는다. 요구사항('고유 exact-name profile 동작 유지')상 허용되지만, 같은 이름의 미연결 수기 행과 분류된 profile이 공존하게 된다. 이 행을 운영 확인 대상으로 인계 기록에 남겨야 한다.
- 새 픽스처 행을 추가하면 기존 테스트의 위치 기반 배열 단언(scheduleGroups 13개, 이름 목록 단언의 마주옥·오진주 등 null profile/그룹 기대값)이 바뀐다. 새 id 대역을 쓰고, 기존 단언은 의도가 유지되는 범위에서만 조정해야 한다.
- 보존 케이스 검증에는 department·job_group·profile_user_id가 그대로인 것뿐 아니라 재실행 후에도 같은 이름 roster 행이 늘지 않는다(중복 INSERT 없음)는 단언도 포함하는 것이 좋다.
- 고유 profile이 있는 이름과 profile이 없거나 동명이인인 이름 각각에 대해 수기 분류 미연결 행 케이스를 넣어야 두 분기(연결 분기, 미연결 job_group 분기)가 모두 검증된다.

## 더 나은 순서 · 제안
- 픽스처에 (a) 고유 profile + 수기 분류 미연결 roster, (b) profile 없음 + 수기 분류 roster, (c) NULL/공백/미지정 roster를 한꺼번에 추가한 뒤 재현 실패를 확인한다.
- SQL 수정 시 연결 분기와 미연결 분기에 같은 '미지정 판정' 조건(department IS NULL OR btrim(department)='' OR department='미지정')을 동일하게 적용한다. 재실행 경로(두 번째 migration 실행)에서도 보존되는지 같은 테스트 안에서 확인한다.
