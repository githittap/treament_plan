## 기타 지적
- The plan does not say what happens when a uniquely matched profile already has a non-NULL `job_group` that differs from the confirmed roster. The existing test checks that manual classification survives a rerun (e.g., id(1) stays 'desk'). If the seed overwrites values on every run, a later rerun could undo a reclassification made in the UI, which conflicts with the requirement to preserve actual change data. Specify one rule up front: either write only when the value is NULL, or apply once and then only report differences.
- The same-name check is ambiguous. If duplicate profiles already have linked `schedule_people` rows from unified_schedule_roster, that check will also find them. Setting `schedule_people.job_group` on those linked rows would break the existing guard 'linked schedule people must use profiles.job_group'. Split the cases: an existing unlinked same-name row gets `job_group` only, and a linked row is left alone and reported. Add a test for this.
- The `profiles` fixture in `pglite-employee-job-groups.mjs` has no `name` column, so name matching cannot be tested as is. The fixture must add `name`. Keep the existing `dept`-based backfill and Dr. exclusion assertions, and add the new rows alongside them.
- The existing assertion `doesNotMatch(/대표자|직인|병원 주소/)` in `pglite-employment-certificate.mjs` must change because the representative and address are now expected. Keep a negative check for seal image, base64, and Storage path strings (e.g., `<img`, `data:image`, `storage`). Also confirm that previously issued `issued_html` snapshots do not change when the function is replaced.
- Pass the representative and address through `employment_certificate_escape` or insert them as literals inside the format string. Say explicitly that neither may be added to the `employment_certificates` table columns (schema change) or that any such change is additive only.
- The original request limits record updates to the relevant rows of the requirements tracking table and the implementation results. The BUSD `[허브결정]` note and the `_인계` storage are writes outside that. They are local files and low risk, but record that they are outside the requested scope.
- The confirmed staff names will be committed into the SQL seed in the public repo. The owner has already provided the names, so this is not grounds to block, but state in the report that personal names are included in a public repo. Whether to publish them is the owner's call.

## 더 나은 순서 · 제안
- Before touching the SQL, add the new cases (exact/unique/duplicate/no match, Dr., rerun preserving manual values) to the PGlite test fixture and confirm they fail first.
- Separate the certificate change (fixed representative/address) and the roster seed into their own commits or verification steps, so a failure can be isolated to one side.
- Run the plan's static check for seal exposure (`git grep` for image/base64/storage/absolute path patterns) immediately before the commit, as a separate step from `git diff --check`.
