# 직원허브 P3/G1 6개 기존 SQL 차이분 준비 계획 — 2026-09-26

## 목표

통합 worktree 기준 HEAD `57d0ce4`와 선행 카탈로그 대조의 기준 `59d30d0` 사이에서 여섯 SQL 및 그 의존 객체 정의가 바뀌었는지 먼저 확인함. 그 뒤 기존 객체가 있는 SQL 6개(notice snapshot, push outbox, consultation journal, attendance release, attendance_manual_v2, monthly leave accrual)의 확인된 카탈로그 차이와 현재 저장소 초안을 대조함. 전체 SQL을 재실행하지 않고, 현행 데이터·RLS·ACL·함수 권한을 보존하는 최소 delta 파일만 로컬 `db/`에 준비하며 오프라인 시험으로 확인함. 이전 증거의 보류 사유가 해소되고 현재 소스/승인된 목표가 정확히 뒷받침하는 경우만 작성하고, 그렇지 않으면 보류함.

## 범위와 금지

- 허용: 지정 통합 worktree의 읽기, 기존에 승인된 범위의 SELECT-only 운영 카탈로그 조회, `db/` 새 delta 파일, 그 파일과 직접 관련된 오프라인 시험, 지정 T8 `_증거`와 `구현결과.md` 기록.
- 금지: 원본 repo root·타 worktree 쓰기, 기존 SQL 수정/통째 재실행, 운영 DB DDL/DML/RPC 호출, Storage·Edge·secret·Cafe24·main push·운영 권한 시험.
- 모든 delta는 로컬 초안이며 G3 배포 승인으로 볼 수 없음. 계정별 API/역할 시험과 PITR/복구점이 확인되지 않은 상태를 각 초안 적용 전 gate로 남김.
- 월차는 첫해 1~11개월의 월차만 생성하고, 1주년 다음 날 연차 15일을 기록하며 이후 추가 월차는 만들지 않는 요구를 보존함. 운영 적용 전 원장이 누적 산정 결과와 적용 기준을 확인하는 별도 관문이 필요함.

## 진행 순서

1. BUSD 상태와 worktree 대상 잠금을 읽고, 지시서 0장·P3 계획·운영 사전준비 증거·30 SQL 분류·Supabase/위임/인계 지침을 대조함.
2. 기존 기준 `59d30d0`에서 이번 `57d0ce4`까지의 여섯 SQL 및 관련 객체 정의 diff를 읽어 선행 운영 카탈로그 지문이 여전히 적용되는지 확인함. 달라진 정의가 있으면 해당 항목은 현행 메타데이터를 다시 SELECT-only 확인하기 전 보류함.
3. 후보마다 이전 보류 사유가 해소되었는지, 승인된 요구 정의와 오프라인 시험이 최소 delta를 정확히 뒷받침하는지 판정함. 보류 사유가 계속되거나 목표 정책·함수 계약·권한 의미가 불명확하면 delta를 작성하지 않음.
4. 안전 근거가 강한 순으로 1~2개를 먼저 완결함. delta 파일은 현재 상태 guard와 재실행 안전성을 갖추고, 기존 데이터를 재해석·삭제하거나 권한을 넓히지 않음. 각각 직접 관련된 오프라인 시험만 추가/실행함. 안전한 후보가 없으면 0개 작성으로 끝내고 blocker를 기록함.
5. 6개 전체 판정, 작성/보류 사유, 시험 결과, 남은 운영 gate를 기존 증거와 `구현결과.md`에 기록함. 계획 및 계획 검토 파일은 `_인계`에 로컬 미커밋으로 유지하고, 기록은 기존 파일 역할에 맞춰 끝에 이력으로 추가하며 타인 소유 파일을 덮어쓰지 않음.

## 완료 기준

- 여섯 SQL 각각에 대해 delta 작성 또는 보류가 근거와 함께 표시됨.
- 새 파일은 모두 지정 worktree `db/`의 delta 파일이며 원본 SQL은 변하지 않음.
- 각 작성 파일에 관련 오프라인 시험 결과가 있음. 전체 JS 시험 수치는 앞선 423/423 결과이며, 이번에는 SQL delta 관련 시험만 실행함. 커밋하지 않으며 baseline 재검증은 하지 않음.
- 운영 쓰기·RPC 호출·배포·main push는 0건임. PITR/API 역할 시험 미확인은 적용 전 gate로 분명히 기록됨.
