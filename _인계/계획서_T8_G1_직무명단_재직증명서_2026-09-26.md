# T8 G1 로컬 미완료 구현 계획 — 직무 명단·재직증명서

## 목표와 기준선

지정 worktree `integrate/employee-hub-phase2-local-20260925`에서 원장 확정 명단을 기존 근무표 로스터와 안전하게 연결하고, 재직증명서 발급본에 확정 대표자·주소를 넣는다. 기준 HEAD는 `6e01251`; 운영 DB와 배포에는 손대지 않는다.

## 허용 범위

- `db/unified_schedule_roster.sql`, `db/employee_job_groups.sql`, `db/employment_certificate_draft.sql`
- 직접 관련 시험 `tests/sql/pglite-employee-job-groups.mjs`, `tests/sql/pglite-employment-certificate.mjs`, `tests/schedule-roster.test.js`
- T8 정본의 `요구추적표.csv`, `구현결과.md`에서 대상 요구 행/절만 갱신
- 이 계획·요청 및 검토 기록을 worktree `_인계`에 저장하고, 로컬 commit

원본 repo root, 다른 worktree, 그 밖의 제품 파일은 수정하지 않는다. 운영 SQL, Storage, Edge, secret, main push, Cafe24, 실기기 및 외부 서비스 조작은 금지한다. 실제 직원 행·식별자·운영 profile 값은 조회하거나 추정하지 않는다.

## 구현 판단

1. 네 일반 그룹 이름과 멤버는 `요청_T8_G1_직무명단_재직증명서_2026-09-26.md`에 적힌 원장 확정 목록 그대로 사용한다. Dr. 원장과 의사 명부는 별도 유지한다.
2. 기존 업무표 명부·schedule row는 보존한다. 이름이 정본과 정확히 일치하는 profile이 1개인 경우에만 연결한다. 0개 또는 복수이면 user/profile 연결을 만들지 않고 이름 항목만 표시·보고한다. ID, 계정, 권한을 추정하거나 새 계정을 만들지 않는다.
3. 기존 SQL의 drop/recreate, schedule row 삭제, 과거 schedule 수정, 권한 확대를 피한다. 재실행 안전성과 충돌 시 중단 조건을 오프라인 시험으로 확인한다.
4. 명단 seed는 `db/employee_job_groups.sql`에 둔다. 유일하게 일치하는 기존 profile의 직무는 `profiles.job_group`에만 기록하고, 연결된 `schedule_people` 행을 재사용한다(`schedule_people.job_group`은 연결 profile이면 NULL 유지). Dr.로 연결된 profile은 네 그룹에 넣지 않는다. 정확·유일한 profile이 없을 때만 동일 이름의 기존 schedule_people를 먼저 확인한 뒤 미연결 명부 행을 추가하며, 기존 같은 이름 행이 있으면 중복 생성하지 않는다. department와 schedules는 건드리지 않는다.
5. 재직증명서에는 대표자 `정용태`와 주소 `충청남도 아산시 온천대로 1065, 이안빌딩 4층 401~403호`를 고정한다. 기존 발급 HTML은 DB에 저장되고 프런트가 그대로 DOM에 표시함을 확인했다. G1의 소유 파일에는 사설 Storage의 다운로드/서명 URL 처리기가 없고 G4도 미승인이다. 따라서 이번 SQL/시험에는 직인 이미지 바이트, base64, 로컬 절대 경로, 외부 이미지 URL, Storage 버킷명·객체 경로를 넣지 않고 직인 이미지 삽입은 보류한다. 실제 직인 출력은 승인된 private asset 경로와 발급/표시 연결을 가진 별도 G1 프런트 변경 및 G4 설정 뒤에 가능하다고 기록한다.

## 순서와 검증

1. 이 요청 요약, 구현지시서 0장, 남은구현계획 맨 위 원장 답/P1-5/P3, 구현결과 최신 감사 절, delegation/busd/session-handoff, Supabase 스킬, 비용 KB를 확인한다. BUSD 상태·worktree·현재 잠금을 확인한다.
2. 지정 DB SQL과 직접 관련 시험을 읽어 기존 데이터·권한·발급 동선을 보존할 최소 변경을 설계하고, 이 계획에 대한 Opus 5.5/high 검토를 실행한다. `opus_review.py check`가 PASS 전에는 구현 파일을 바꾸지 않는다. FAIL이면 중대한 지적이 없더라도 1회만 계획을 보완하고 재검토한다.
3. 검토 통과 후 SQL/직접 시험과 T8 대상 기록 행만 최소 수정한다. 시험에는 정확·유일 profile 연결, 미일치·중복 profile 미연결, Dr. profile 예외, 재실행 멱등, 기존 schedules 행 보존, 네 그룹의 정본 멤버·카운트, 대표자·주소, 재직증명서 권한·스냅샷을 포함한다. 직인 원본과 사설 Storage 식별 문자열은 repo 어디에도 복사·인라인하지 않는다.
4. PGlite 그룹 시험, PGlite 재직증명서 시험, `schedule-roster.test.js`를 각각 한 번 실행한다. 실패가 있으면 원인을 수정하고 해당 실패 시험만 한 번 재실행하며 실패/재시도 기록을 남긴다. 변경 후 `git diff --check`, 정확한 대상 파일 목록·직인 자료 비노출 여부를 확인하고 로컬 커밋한다.
5. 구현결과에 요구별 완료/부분/보류, 파일·시험·커밋, 직인 저장/표시 제한, 운영 승인 게이트를 기록한다. 요구추적표는 대상 4개 요구 행만 최신 증거에 맞춰 갱신하고 이력을 지우지 않는다. BUSD 인계는 요구추적표와 별개로 기존 `[허브결정]` 행의 note만 추가하고 그 밖의 행/필드는 바꾸지 않는다.
